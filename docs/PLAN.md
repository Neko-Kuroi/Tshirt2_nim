# tshirt2 Nim 移植計画

在庫管理アプリ (Flask 版) を Nim へ移植する計画。進め方は Go 版移植 (手順0〜6) と同じ型に揃え、各手順の終わりで止まって結果を報告する。

## 目的

- Flask 版在庫管理アプリを Nim の単一バイナリに移植し、配布と運用を軽くする
- 画面・業務規則・文言・計算値は Flask 版と一致させる
- 品質の正本は Flask 版のテスト151件と、Flask 版から生成した照合データ

## 不変条件 (Go 版と同じ)

- 同じ `inventory.db` を無変更で共用する (スキーマ、`PRAGMA user_version`、保存値の形式を変えない)。Flask 版・Go 版への切り戻しが常に可能であること
- パスワードハッシュは Werkzeug 互換 (scrypt / pbkdf2) を読み書きできること
- 切替時の利用者影響は「全員が1回ログインし直す」だけに留める

## 再利用できる資産

| 資産 | 内容 |
| --- | --- |
| Go 版 `tools/` の生成物 | マイグレーション、util ベクトル (to_int / strip / size_key 647件)、ゴールデン DB・CSV・一覧77条件、Werkzeug ハッシュベクトル。言語非依存の JSON/CSV なので Nim 側テストがそのまま使える |
| Go 版 DESIGN.md | セッション / CSRF / Tx / BUSY リトライ / ドットセグメント等の設計判断は言語非依存。そのまま Nim 版の実装仕様になる |
| amezo-nim の vendor nimcrypto | `scrypt.nim` / `pbkdf2.nim` / `hmac.nim` を同梱済み (この環境で確認済み)。最大のリスクだったハッシュ互換に手持ちの実績資産がある |
| amezo-nim の FFI パターン | libz を直接叩いた前例。SQLite を FFI で使う場合の型になる |
| この環境 | Nim 2.4.0 (choosenim) 導入済み、libsqlite3 ランタイムあり |

## 技術選定 (手順0のスパイクで実測して決める)

1. **HTTP サーバー**：候補は mummy (スレッド型、同期ハンドラー) / jester + httpbeast / 標準 asynchttpserver / amezo 式の自前。判断基準は「同期 SQLite との相性」「フォーム処理と Cookie の扱い」「静的配信を自前に差し込めるか」。非同期サーバーに同期 DB を直結するとイベントループを止めるため、スレッド型か、非同期＋ワーカースレッドの構成が本命。
2. **SQLite バインディング**：リンク方式は**動的リンク前提で確定** (配布先に libsqlite3 がある前提。amalgamation の静的リンクは採らない)。残る候補は db_connector (nimble 取得) / FFI 直叩き (amezo 式) で、接続ごとに WAL・FK・busy_timeout を設定できることが必須条件。
3. **テンプレート**：自動エスケープの規律をどう担保するかが要点。候補は nim-mustache (通常の `{{ }}` はエスケープが既定) / 自前ミニテンプレート (Go 版の base＋block 構成を模倣) / DSL 式の HTML 生成。全ページでエスケープ漏れを防ぐ仕組みを、テスト (特殊文字の品番等を含むゴールデン照合) とセットで決める。
4. **暗号**：vendor nimcrypto の scrypt / pbkdf2 を、Go 版が使った Werkzeug ハッシュベクトルで照合する (Go 版の手順0と同一プロトコル)。署名 (HMAC-SHA256) も同梱で賄う。
5. **nimble の取得可否**：この環境からパッケージを取得できるかを最初に確認する。不可なら必要分を vendor 化する (amezo の前例どおり)。

## 手順

- 静的ファイル・テンプレートの埋め込み方法の確認、バイナリサイズの実測 (目安: amezo-nim の実績から 1〜3MB 級を見込む)
- **合格条件**：選定が根拠付きで確定し、ハッシュベクトルが全件一致

### 手順2：サービス層

- **合格条件**：Go 版の web 基盤テスト相当 (認証・セッション・CSRF の実測表を含む) が通る

### 手順4：画面 (16件)

- **合格条件**：同じ DB で Flask 版と主要画面の表示テキストが完全一致 (Go 版とも比較可能)

### 手順5：CLI・ビルド

- **合格条件**：Flask 版 test_cli / test_create_user 相当が通り、実バイナリで一連の操作が動く

### 手順6：並行稼働・切替

- 余力で Flask / Go / Nim 三者の並行稼働も確認する
- **合格条件**：17項目全合格、検証後も user_version=3・integrity ok・スキーマ完全一致。切替手順書を README に記載

## 手順7 (任意)：3実装の比較評価

共存の目的は稼働先の見極めなので、Nim 版の完成後に同じ物差しで3実装を並べて測る。

- バイナリ/配布物の大きさ、起動時間、待機時・負荷時のメモリ (RSS)
- ログイン応答時間 (scrypt は弱い CPU で効く。SoC では体感差になりうる)
- SQLite の読み書き速度 (Go 版の純 Go ドライバーと、C 実装を使う Python / Nim で差が出る可能性がある)
- 稼働先ごとの前提：デプロイサービス (Python がそのまま動くか、バイナリ配置型か) / SoC (ARM 対応、メモリ量、SD カード上での SQLite の耐久性、消費電力)

## 規模の見込み

Go 版の実績は実装 5,932 行＋テスト 5,175 行 (192件)。Nim は同等機能をより少なく書けるため、実装 4,000 行前後＋同等のテスト量を見込む (推定)。照合データと設計仕様が既にある分、手順2以降は Go 版より速く進むはず。

## 手順0 スパイク結果 (2026-11-03、~/workspace/spike-nim)

- **ハッシュ互換：合格**。nimcrypto (amezo-nim の vendor) で Werkzeug ベクトル **11/11 一致** (scrypt、pbkdf2 の sha1/sha256/sha512、日本語パスワード含む)。生成方向も Werkzeug 本体の `check_password_hash` で検証済み。注意点：nimcrypto の `toHex` は大文字を返すので、Werkzeug 形式では小文字化が要る
- **nimble：この環境ではパッケージ一覧の取得に失敗**する。ただし **git clone は通る**ため、依存は全て git から vendor 化する方針で確定 (amezo の前例どおり)。db_connector は Nim ツールチェーン同梱分からも取れる
- **SQLite：db_connector (vendor) で確定**。Flask 版ゴールデン DB を読み (user_version=3)、BEGIN IMMEDIATE の書き込みも動作。libsqlite3 は実行時に動的ロードされ、前提 (動的リンク) と一致
- **サーバー：mummy 0.4.8 (vendor) で確定**。スレッド型で、リクエストごとの SQLite 読み取りと並行10リクエストを確認。依存の webby / zippy / crunchy / nimsimd も vendor 化する
- **テンプレート：nim-mustache (vendor) を採用**。`{{ }}` は HTML エスケープが既定であることを確認 (`{{{ }}}` が明示的な raw)。部品分割は partial で Go 版の `_*.html` に対応させる
- **埋め込み**：`staticRead` で静的ファイルをバイナリに含め、配信できることを確認
- **サイズ実測** (release、--opt:size、strip 後)：サーバー＋SQLite の最小構成で約 **200KB**、nimcrypto 一式で約 **311KB**。完成品も 1〜2MB 級に収まる見込み
- vendor したコミット：db_connector 29450a2、mummy 01deb1f、webby fe515be、zippy c625c0c、crunchy 98eb652、nimsimd dd27017、nim-mustache 274d132

- **手順7で見つけた注意点 → 修正済み**：当初、Nim 版はログイン (scrypt 検証) を処理した mummy ワーカースレッドごとに scrypt の作業メモリ約34MB が RSS に残り続け、待機しても戻らなかった (実測：起動時 7.4MB → ログイン1回 41MB → 5回 177MB。ワークロード全体では 229MB)。切り分けの結果、リークではなく Nim のアロケータが解放した大きなブロックを自分のフリーリストに保持して OS に返さないことが原因と判明 (単一スレッドでは再利用されて増えず、スレッド数ぶんだけ保持が増える)。対策として src/passwords.nim の scryptKey で作業領域 (xyv/b) を C の malloc/free で確保するよう変更 (この大きさは mmap され、free で OS に返る)。修正後の実測：サーバーで待機時 5.5MB → ログイン負荷後も約43MB で安定し、それ以上増えない (残りは各ワーカーのヒープ保持分)。テスト214件は全合格を維持
- **Go 版の同種の問題 → 修正済み**：ユーザーの指摘で Go 版も同じ観点で再検証したところ、リークではないものの、検証1回あたり約34MB の作業領域が「解放済みだが GC 未回収」のまま残り、並行ログインで RSS が一時約630MB まで膨らんでいた (待機中は割り当てが無く GC が走らないため)。Go 版 internal/auth に、派生処理の同時実行セマフォ (最大4) と、派生ごとの debug.FreeOSMemory() による OS への返却を追加。修正後のサーバー実測：待機時 10.9MB → ログイン負荷後も約18MB で一定 (修正前は並行10回で 338.8MB)。Go 版テスト192件は全合格を維持し、GitHub 用パッケージ側にも同じ修正を反映済み
- **テスト総数：214件、全合格** (DB 23、util 17、パスワード 3、サービス 63、Web 基盤 53、画面 12+13+7、CLI 23)
